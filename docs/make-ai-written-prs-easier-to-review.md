# 如何让 AI 写的 PR 更容易 Review

上一篇《[AI 写代码越快，我们越需要认真看代码](./ai-writes-code-humans-still-review.md)》讨论了一个矛盾：AI 生成代码的速度正在超过人类理解代码的速度。代码写得越快，团队越需要通过 Review 保持对项目的控制。

但只强调“认真看”还不够。

当一个 PR 包含几十个文件、上千行改动时，让 reviewer 直接面对原始 diff，再要求他认真理解全部上下文，本身就是一种低效的工作方式。

我们还需要解决另一个问题：

> 怎样把 AI 写出的 PR，变成人更容易 Review 的形状？

## Reviewer 缺的不是更多文字

很多 AI 生成的 PR 描述都很完整：修改了哪些文件、增加了哪些类、运行了哪些测试，往往一项不少。

但这些内容仍然没有回答 reviewer 最关心的问题：

- 为什么要改？
- 用户会观察到什么变化？
- 修改前后的运行路径有什么不同？
- 最大风险在哪里？
- 哪些地方需要人作出决定？
- 测试证明了什么，又没有证明什么？

问题不在于信息太少，而在于信息仍然按照代码生成过程组织。Reviewer 必须自己把文件列表和实现细节重新拼成系统行为。

## `/show-me` 提供了一种启发

[`/show-me`](https://github.com/humanlayer/skills/blob/main/plugins/show-me/skills/show-me/SKILL.md) 是 Dex Horthy（[@dexhorthy](https://github.com/dexhorthy)，HumanLayer）发布的一款面向编码 Agent 的 Skill。它的核心不是生成更精美的图，而是：

> 选择能够说明问题的最小视图。

局部逻辑用伪代码，运行路径用调用树，UI 用组件树，职责变化用文件树，复杂交互才使用流程图或 HTML。如果原有结构基本不变，就直接用 `diff` 形状标出变化。

例如，一个保存操作增加缓存后，与其写几段说明，不如直接展示：

```diff
 on(save)
-  write content
+  if content is unchanged
+    return cached result
+  write content
+  invalidate cache
```

Reviewer 一眼就能看到行为变化，也能立刻追问：缓存什么时候失效？并发保存是否可能返回旧结果？

`/show-me` 本身不是代码检视工具，但它指出了一个重要原则：**如果想让人作出更好的判断，先要让信息适合人理解。**

## 好的 PR 应该先给出一张变更地图

AI 不应该只替 PR 补一段更长的摘要，而应该先整理一张由浅入深的变更地图。

第一屏只需要呈现最重要的信息：

- 一句话说明为什么改、改了什么；
- 一个“修改前 → 修改后”的最小行为视图；
- 最高优先级风险；
- reviewer 必须确认的决定；
- 已执行验证的真实状态；
- 建议从哪里开始 Review。

看完这一屏，reviewer 应该已经知道这次改动的轮廓，以及自己的注意力应该放在哪里。

随后再按需展开调用方、关键代码、影响矩阵、测试结果和原始 diff。摘要负责建立心智模型，详细证据负责支持判断。两者不能互相替代。

## 按行为组织，而不是按文件组织

一个功能通常会同时修改配置、接口、运行时逻辑、指标和测试。如果 PR 描述按照文件顺序逐项介绍，完整行为会被拆散在多个段落中。

更好的方式是按照因果链组织：

```text
配置如何进入系统
   ↓
运行时如何使用它
   ↓
状态和失败如何处理
   ↓
指标如何反映结果
   ↓
测试如何证明行为
```

文件和代码行仍然重要，但它们应该作为证据链接到行为，而不是成为 PR 描述的主结构。

## AI 做第一轮，人做第二轮

前一篇文章强调人工 Review，并不是排斥 AI 检视。更合理的分工是：

- **AI 做第一轮**：读取 diff、调用方、测试和历史，快速扫描缺陷与影响，再把结果整理成简洁视图和可追溯证据；
- **人做第二轮**：确认业务行为、架构取舍、兼容性和风险是否可以接受，并作出最终合入决定。

AI 的价值不只是帮人找 Bug，也包括降低人建立系统心智模型的成本。它应当把 reviewer 从“整理材料”中解放出来，而不是把判断本身拿走。

## 优化后的 Skill 做了什么

基于这一思路，我们优化了 [`explain-diff-for-human-review`](../skills/explain-diff-for-human-review/SKILL.md)：

- 报告深度随改动规模和风险变化，小修改不再强行套用完整架构模板；
- 先建立变更地图，再组织详细证据；
- 根据问题选择伪代码、调用树、组件树、文件树、流程图或 `diff` 视图；
- 第一屏集中展示行为变化、最高风险、待确认决定、验证状态和 Review 顺序；
- 事实、声明的意图和推断分别标记，避免把 AI 的解释伪装成代码事实；
- 原始 diff、长代码和验证命令折叠到需要时再展开。

它仍然不会替人批准 PR。它做的是把一个难以阅读的代码改动，整理成一份适合人作出判断的案卷。

## Review 正在成为新的效率瓶颈

当 AI 可以同时生成更多代码和更多 PR 时，团队真正稀缺的资源不再是敲代码的时间，而是理解改动、判断风险和维护系统一致性的注意力。

让 AI 写出更多代码，只提高了生产速度。让 AI 把改动解释成适合人理解的形状，才能同时提高 Review 的速度和质量。

AI 负责把 PR 讲清楚，人类负责决定它是否应该进入系统。
