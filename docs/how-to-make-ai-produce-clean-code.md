# 如何让 AI 产出 Clean Code

上一篇讨论了 Vibe Coding 项目如何因未经验证的假设逐渐腐败。但即使需求判断正确，Agent 生成的代码仍可能因为职责混乱、重复和耦合而变成“大泥球”。前一篇治理需求与假设，这一篇讨论如何治理代码与架构。

AI 编码代理让代码生产速度达到前所未有的水平。过去需要几天完成的功能，现在可能一小时就能交付。

但生成得快，不等于代码干净。

如果只要求“实现功能并通过测试”，Agent 很容易堆叠分支、复制逻辑、拉长函数，并在原有模块上继续增加职责。每一次修改都可能局部合理，累积起来却会让系统变成难以维护的“大泥球”。

> AI 不会自动产出 Clean Code。我们必须先定义质量，再测量结果，用约束和反馈持续逼近它。

## 为什么 AI 容易写出脏代码

Agent 擅长根据当前上下文生成最可能成立的实现，但它不会天然为半年后的维护成本负责。

当需求只描述功能结果时，它通常优先选择最直接的路径：

- 在已有函数中增加一个分支；
- 复制并修改相似逻辑；
- 让新模块直接依赖现有实现细节；
- 用更多状态和配置兼容旧行为；
- 生成能证明当前实现的测试。

这些选择未必立即出错，却会逐渐破坏职责边界和架构一致性。开发者的角色因此需要从“亲自写每一行代码”，转向“定义规则、提供反馈并判断取舍”。

## 一、先定义什么叫“干净”

“让代码更优雅”不是可执行要求。Agent 需要能够验证的质量标准，例如：

- 新代码不得引入明显重复；
- 函数和模块只承担清晰、可描述的职责；
- 业务层不能反向依赖基础设施实现；
- 圈复杂度、重复率和 CRAP 分数不能超过团队阈值；
- 公共接口必须有稳定的行为测试；
- 新增依赖必须说明理由和影响范围。

函数行数、复杂度和覆盖率都只是风险信号，不是 Clean Code 的定义。指标的作用是触发检查，最终仍要回答：这段代码是否容易理解、修改和验证？

## 二、用测试保护行为

重构的前提，是我们知道哪些行为不能被破坏。

可以先把需求写成验收场景，再让 Agent 补充单元测试和属性测试。对于结算、权限、解析器等高风险模块，还可以使用 Mutation Testing 检查测试是否真的能发现错误。

但测试不能证明一切：

- 测试通过，不代表需求前提正确；
- 覆盖率高，不代表断言有效；
- 杀死所有变异体，也不代表架构合理。

测试的职责是保护行为，让 Agent 能够安全重构；它不能代替对需求、边界和设计的判断。

## 三、用多层约束保护结构

只靠 Prompt 提醒 Agent“注意代码质量”并不可靠。约束应该进入自动化流程：

1. **代码层**：格式化、Lint、类型检查、重复代码和复杂度分析。
2. **测试层**：验收测试、单元测试、属性测试，以及按风险使用的 Mutation Testing。
3. **架构层**：依赖方向、模块边界、循环依赖和公共 API 检查。
4. **交付层**：性能基准、安全扫描和兼容性验证。

例如在 Go 项目中，可以用 [`golangci-lint`](https://golangci-lint.run/docs/linters/) 统一启用 `staticcheck`、`govet`、`gosec`、`gocyclo` 和 `dupl`，覆盖缺陷、安全、复杂度与重复代码；再用 [SonarQube](https://docs.sonarsource.com/sonarqube-server/user-guide/code-metrics/metrics-definition) 观察项目级代码异味和可维护性趋势。团队还可以加入自定义检查工具，以及承担架构、安全或代码质量等特定检视角色的 Agent，用来检查通用分析器无法理解的项目规则。

把这些检查接入 CI，未达到团队基线的修改不能合入。失败结果必须足够具体，能够直接变成 Agent 的下一轮重构任务。

```text
生成代码 → 自动测量 → 暴露问题 → 定向重构 → 再次验证
```

这比让 Agent 自我评价“代码已经很干净”可靠得多。

## 四、把生成过程拆成几个阶段

不要让同一个 Prompt 同时承担需求分析、编码、测试、重构和架构审查。可以把过程拆开：

- **规格阶段**：把模糊需求转化为可验证行为，明确边界和失败场景。
- **实现阶段**：先建立行为测试，再完成最小实现。
- **重构阶段**：专门消除重复、降低复杂度、改善命名和职责划分。
- **架构阶段**：检查依赖方向、模块边界和系统一致性。
- **代码检视**：先由 AI 全面检查，再由人类确认业务、架构和长期代价。

前面写了篇[《AI 写代码越快，我们越需要认真看代码》](./ai-writes-code-humans-still-review.md)，有同事误解为在排斥 AI 检视。其实那篇文章强调的是人工检视的重要性，并不意味着代码只能由人检查。更有效的方式是把检视分成两轮：

- **第一轮由 AI 检视**：快速扫描更大的改动范围，发现明显 Bug、安全漏洞、风格问题和遗漏的测试。它不会因疲劳或时间压力而主动缩小检查范围。
- **第二轮由人类检视**：重点判断业务逻辑是否正确、架构取舍是否合理，以及代码能否长期维护。

AI 适合提供第一轮全面、快速的检查，人类负责第二轮判断和最终决策。

不同阶段可以由不同 Agent 执行，但“多 Agent”本身不是质量保证。真正有效的是职责分离、独立证据和明确的合入标准。

## 让每次修改都减少一点混乱

Clean Code 不是一次性生成的结果，而是持续迭代出来的状态。

实践中可以从小模块开始，为代码库建立一组简单而稳定的规则。每次提交都要求：

- 不让关键指标恶化；
- 新增复杂度必须有业务理由；
- 修改过的代码比修改前更容易理解；
- 临时兼容逻辑必须记录退出条件；
- Agent 无法确认的设计决定交给人类。

当这些要求成为自动化门禁和团队习惯，AI 的速度才会转化为真正的生产力，而不是更快地制造技术债务。

## 人类仍然负责系统质量

工具可以测量复杂度，测试可以保护行为，Agent 可以快速重构，但它们无法替团队决定：

- 哪些复杂度来自真实业务；
- 哪些抽象值得长期维护；
- 哪些风险可以接受；
- 系统应该朝什么方向演进。

AI 时代的 Clean Code，不再只是程序员的个人美德，而是可持续交付的基础设施。

让 AI 写得更快并不难。真正重要的是建立一套机制，让它每次写完之后，都能被测量、被质疑、被改进，并最终保持在人类可以理解和治理的范围内。
