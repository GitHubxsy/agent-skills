# 如何让 AI 写的 MR 更容易 Review

在《[AI 写代码越快，我们越需要认真看代码](./ai-writes-code-humans-still-review.md)》中，我讨论了一个问题：AI 生成代码的速度正在超过人类理解代码的速度，因此代码检视比过去更重要。

但只要求 reviewer “认真看”还不够。

当一个 MR 包含几十个文件、上千行改动时，如果输入仍然只有原始 diff 和一段泛泛的摘要，理解成本就被全部转移给了 reviewer。

> 让 AI 写出的 MR 更容易 Review，不是让它写更多说明，而是让它把改动整理成人容易判断的形状。

## Reviewer 缺少的是变更地图

很多 AI 生成的 MR 描述看起来很完整：修改了哪些文件、新增了哪些函数、运行了哪些测试，往往一项不少。

但 reviewer 真正需要先知道的是：

- 为什么要改？
- 用户或调用方会观察到什么变化？
- 哪条运行路径或职责边界发生了变化？
- 最大风险和待确认决定是什么？
- 测试证明了什么，又没有证明什么？
- 应该先看哪段代码？

文件列表只是证据，不应该成为描述的主结构。好的 MR 应该先提供一张 Review 地图，让人快速建立整体认识，再沿着链接和 diff 深入核验。

## 用最小视图说明变化

[`/show-me`](https://github.com/humanlayer/skills/blob/main/plugins/show-me/skills/show-me/SKILL.md) 提供了一个很有价值的原则：选择能够说明问题的最小视图。

局部逻辑用伪代码，运行路径用调用树，UI 用组件树，职责变化用文件树，复杂交互才使用流程图。已有结构只发生局部变化时，直接展示 `diff` 形状。

例如，一个保存操作增加缓存后，与其写几段说明，不如展示：

```diff
 on(save)
-  write content
+  if content is unchanged
+    return cached result
+  write content
+  invalidate cache
```

Reviewer 一眼就能看出行为变化，也能立即追问：缓存何时失效？并发保存会不会返回旧结果？

可视化的目的不是让 MR 更漂亮，而是减少人从文件和代码行中重新拼装系统行为的成本。通常一到三个视图就够了。

## 第一屏只呈现最重要的信息

一个适合 Review 的 MR，第一屏应该回答：

```text
Why        为什么改
Behavior   外部行为发生了什么变化
Risk       最大风险或需要确认的取舍
Start here 最值得先看的文件或符号
Validation 实际执行了哪些验证
```

随后再用最小视图解释调用链、状态变化或模块职责。原始 diff、长日志和完整测试输出不需要塞进描述，它们应该作为继续核验的证据存在。

这里最重要的是区分三类信息：代码中能确认的事实、需求中声明的意图，以及 AI 根据上下文作出的推断。不能把推断包装成确定结论。

## 仓库模板不能替代具体改动说明

很多团队已经配置了 MR 模板，用来询问影响范围、回滚方案、安全风险或发布步骤。这些问题代表团队长期积累下来的治理规则，AI 不应该绕过。

但仓库模板通常不了解本次改动，也不能替代 Review 地图。更合理的组合是：

```text
本次改动的 Review 地图与结构视图

---

仓库配置的 MR 模板
```

AI 能从需求、代码、diff 和验证结果中确认的内容就据实填写；无法确认的字段留空，未经验证的检查项保持未勾选。

留空不是失败，而是在明确告诉 reviewer：这里仍然缺少答案，需要人补充或作出决定。相比为了“填完整”而编造一个合理答案，这种不确定性更有价值。

## AI 做第一轮，人做第二轮

强调人工检视，并不意味着排斥 AI 检视。更合理的分工是：

- **AI 做第一轮**：读取 diff、调用方、测试和历史，快速扫描问题并整理 Review 地图；
- **人做第二轮**：确认业务行为、架构取舍、兼容性和残余风险是否可以接受。

AI 的优势是速度快、覆盖面广，对明显 bug、安全漏洞和风格问题检查得比较稳定。人类的价值则在于理解业务承诺、长期架构和那些尚未写进代码的约束。

最终决定仍然属于真正承担项目责任的人。

## 把原则放进提交工作流

我们将这些原则放进了 [`commit-mr`](../skills/commit-mr/SKILL.md)。在内部 CodeHub 环境中，它会完成：

```text
确认任务范围
   ↓
运行验证，只提交相关文件
   ↓
生成 Review 地图和最小结构视图
   ↓
通过 ch 获取并填写仓库 MR 模板
   ↓
推送分支，创建或更新 MR
```

它解决的是提交端的交接问题：不要让 Agent 写完代码后，只留下一个需要人重新考古的 MR。

## MR 的质量决定 Review 的效率

当 AI 可以持续生成更多代码和更多 MR 时，团队真正稀缺的资源不再是敲代码的时间，而是理解改动和判断风险的注意力。

一个好的 MR 不一定更长，但应该让人更快理解行为变化、更早发现未知，并知道从哪里开始核验。

写好 MR 也是开发者的义务。提交代码不只是把分支推到远端，还包括向 reviewer 说明改动目的、行为变化、风险和验证边界，不能把还原上下文的成本全部转嫁给别人。

AI 可以帮助开发者把 MR 讲清楚，但开发者仍然要对描述的真实性和完整性负责；reviewer 则负责决定这次改动是否应该进入系统。
