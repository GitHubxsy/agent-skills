# 我们谈论了太多 SDD，却严重忽视了 SDT

上一篇《[如何阻止 Vibe Coding 项目腐败：把需求对齐做厚](./vibe-coding-alignment-thick-implementation-thin.md)》讨论了如何在编码前暴露假设、邀请真正知道答案的人参与，并把共识变成可验证产物。

但需求对齐只解决了起点。软件还要经历几十次甚至几百次迭代：新的 Agent 不断进入，旧的上下文不断丢失，已经确认的需求仍可能被后续修改悄悄破坏。

我们需要的不只是让 Agent 正确理解一次需求，还要让这些需求在未来仍能被持续校验。

## 实现越简单，需求越需要独立校验

随着 Agent 的长程执行和编码能力继续提升，规划、拆分任务、编码和重构会越来越多地退到 Agent 内部。对边界清楚的常规需求，人类最终可能只需要提交一个 `/goal`。

但 `/goal` 只能告诉 Agent 这一次要去哪里，不能保证后续几十次迭代仍然尊重今天确认的需求。

当实现过程越来越不需要人类介入，真正重要的问题不再是“Agent 准备分几步完成”，而是：

> 什么证据能够准确判断需求是否实现，并在未来发生偏差时及时触发纠偏？

答案是从需求独立产生的高质量测试。

## SDT：把需求变成可执行检查

本文用 SDT 指 Specification-Driven Testing：测试和判定标准直接从规格派生，而不是从已经写好的代码反推。这并不是新概念；NIST 早在 2007 年就记录过[从接口规格生成一致性测试](https://www.nist.gov/publications/specification-driven-testing-smart-card-interface-using-formal-model)的实践。

Spec 记录已经确认的需求，测试把其中可验证的部分变成持续执行的约束。

一段文字可能被不同 Agent 作出不同解释；一个测试则会给出明确结果：当前实现是否仍然满足已经确认的行为。

## “Agent 生成了测试”还不够

如果同一个 Agent 先脑补需求、再写实现、最后根据实现补测试，测试很可能只是重复它自己的理解。代码与测试可以一起全绿，却一起偏离真实需求。

高质量 SDT 至少需要满足四点：

1. **测试来自已确认的规格，而不是当前实现。** 输入包括业务规则、具体示例、边界和失败场景。
2. **判定标准由人检视。** 人类重点确认输入、预期结果和允许的例外，不必逐行审查测试代码。
3. **测试稳定行为，而不是内部结构。** 重构实现不应破坏测试，改变需求才应该修改测试。
4. **需求与测试可以相互追溯。** 每条关键需求对应哪些测试，每个测试保护哪条需求，都应清楚可查。

例如，“支持订单退款”不能只生成一个“退款成功”的用例，还应从规格中派生出：哪些状态可以退款、能否部分退款、累计退款是否超过实付金额、重复请求是否产生二次退款，以及失败后如何恢复。

这些测试不仅仅验证当前实现，而且约束未来每一次实现都遵守已经确认的业务边界。

## 测试应该独立于实现生成

更可靠的 Agent 工作流应该是：

```text
需求对齐
   ↓
形成 Spec、业务示例与边界
   ↓
测试 Agent 独立生成验收测试、契约测试和属性测试
   ↓
产品、测试与开发检视判定标准
   ↓
实现 Agent 编码
   ↓
测试持续校验需求
```

关键不是一定要使用两个模型，而是测试不能以实现代码为答案来源。测试 Agent 和实现 Agent 可以使用同一种模型，但应当从同一份已确认的 Spec 独立工作。

实现 Agent 也不能为了让测试通过而静默修改测试用例。代码与测试发生冲突时，应先判断实现错了，还是需求真的发生了变化；只有后者才能同时修改 Spec 和测试。

## 未来最重要的产物，不只是代码

当 Agent 可以自行规划、实现和重构后，开发者不再需要把主要精力放在描述每一个编码步骤上。需求实现侧真正需要建设的，是一条将需求稳定转换为高质量测试的流水线。

测试当然无法发现所有未知的未知，也不能代替产品判断和探索性测试。但它至少能做到一件极其重要的事：

> 让已经确认的需求，不会在未来的快速迭代中被悄悄改掉。

需求文档定义业务边界，SDT 让这些边界在每一次迭代中都得到自动校验。
