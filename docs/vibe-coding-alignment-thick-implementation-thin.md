# 如何阻止 Vibe Coding 项目腐败：把需求对齐做厚

上一篇《[Vibe Coding 项目是如何一步步腐败的](./how-ai-coding-projects-decay.md)》讨论了腐败的起点：Agent 为了继续执行，把未经确认的假设写进代码；测试再把这些假设包装成“确定事实”，更多模块随后建立在它们之上。

怎样打断这个过程？关键不是让 Agent 少写代码，而是让它在写代码前少猜需求。

最近 [`mattpocock/skills v1.2`](https://github.com/mattpocock/skills/releases/tag/v1.2.0) 的更新，提供了一条值得关注的治理路径：

> 把需求对齐侧做厚，让未经确认的假设更难进入实现。

## 第一道防线：在编码前暴露假设

v1.2 增加了文档、`/wizard` 等实用能力，但更值得关注的是一组围绕“理解需求”的变化：

- `/grilling` 先梳理决策之间的依赖，再按当前可以回答的问题分轮追问；
- `/to-questionnaire` 面向自己无法回答的问题，确认应该询问谁、需要从对方那里获得什么，再生成问卷；
- `/prototype` 把难以在文字中确认的状态和交互，变成可以运行、可以操作的证据；
- `/wait-what` 使用用户熟悉的行业术语重新解释 Agent 的表达。

这些 Skill 看起来功能不同，实际都在解决同一件事：**在 Agent 开始实现之前，让没有说出口的前提变得可见。**

这直接阻断了腐败链条的前两步：Agent 遇到未知后，不再立即把自己的解释当作事实，而是先把它变成需要确认的决定。

## 第二道防线：让真正知道答案的人参与

最初的对齐只发生在“我和 Agent”之间：

```text
/grill-me：我真正想要什么？
/prototype：看到实际效果后，这还是我想要的吗？
```

但很多问题并不在提需求者的脑中，而在产品、设计、测试、运营、财务或法务那里。`/to-questionnaire` 的意义，就是把对齐从个人思考扩展到组织协作：

```text
为了作出这个决定，我还需要向谁确认什么？
```

例如产品提出“支持订单退款”，一句话背后可能藏着许多决定：

- 产品确认整单退款还是部分退款；
- 财务确认手续费和到账规则；
- 运营确认哪些状态允许人工干预；
- 测试把规则转成验收场景；
- 开发实现已经确认的状态机和接口契约。

Agent 可以先暴露决策缺口，生成供相关人员回答的问卷，再把答案转成原型、验收用例和接口契约。各方不再对着模糊文字猜测彼此的意思，而是围绕可运行、可验证的产物校准理解。

所以“对齐侧变厚”并不是文档越来越长，而是让正确的人更早参与，让隐含假设在进入代码前得到确认。

## 第三道防线：让共识成为可验证产物

口头确认仍然容易在传递中失真。已经达成的共识，需要进一步转成原型、验收用例、接口契约或 Spec，让产品、测试和开发能够验证同一件事。

这些产物的价值不是把实现步骤写得更细，而是固定需求边界：哪些已经决定，哪些明确不做，出现异常时应该怎样表现。Agent 可以自行规划实现过程，却不能自行改写这些边界。

## 阻止腐败的新流程

防止腐败，不是为 Agent 编写一份更长的 Plan，而是在假设进入代码前建立一道道确认机制：

```text
模糊意图
   ↓
追问决策缺口
   ↓
邀请相关角色回答
   ↓
用原型、测试和契约验证共识
   ↓
交给 Agent 实现与验证
   ↓
按代码规范和真实需求分别检视
```

我们无法消除所有未知，但可以阻止未知被悄悄当成事实。Agent 越会写代码，人类越不需要告诉它每一步怎么写；但越需要确保所有相关的人，已经对“究竟要实现什么”形成可验证的共识。

Vibe Coding 项目的治理目标，不是降低 Agent 的自主性，而是让自主执行从已经确认的边界开始。

模型决定项目构建得多快，需求对齐决定它是否从一开始就走在正确方向上。
